## 現在の操作

`/?mode=anchor&strategy=direct&detector=april&size=22.5`。strategy省略もdirect。黒い外周15×15cm・白い余白込み22.5×22.5cm。タグの単一姿勢が得られた時点で位置と向きを即採用し、端末移動による独自尺度較正を要求しない。検出器で復号され、既存画素数・再投影の条件を通った一意解ならweakも採用する、意図的にタグを信用する実験である。平面の複数解は即採用しない。

SDK設定はabsolute。メートル単位として扱い、scale=1を用いる。ただしSDK自身の尺度推定・初期化・実機精度を保証するものではない。SDK尺度の収束前に採用した対応が動作時にずれる可能性は残る。

## 位置の扱い

取得時点のタグによる会場カメラ姿勢をA、同時callbackのSDKカメラ姿勢をSとすると、会場とSDKの対応は`A × inverse(S)`。これを更新し、最新SDKカメラ姿勢で表示する。したがって検出間は最後に採用したタグ位置からのSDK相対移動で追跡する。SDKカメラや描画ループはアプリ側で書き換えない。Worker完了時点の最新姿勢に過去画像を直接対応させない。

- 初回の一意なタグ姿勢は即採用。
- 直前のタグ＋SDK予測との差が位置10cm以内かつ回転0.15rad以内なら即採用。徐々に戻す補間は行わない。
- 大きい差は単発で採用しない。1.5秒内に100ms以上離れた3つの固有観測が、会場↔SDK対応として位置5cm・回転0.08rad以内で整合したら、最新のタグ姿勢へ再配置する。
- タグ欠測時は対応を保持する。LIMITED時は非表示、NORMAL復帰後は3観測の再確認を必要とする。hidden・停止・再スキャンで対応を破棄する。

3観測の一致は独立した真値検証ではない。反復する誤検出・共通の姿勢誤差を採用するリスクがあり、暫定ゲートを実機で評価する。タグのばらつきは表示へ直接現れ、再配置は跳びとして見える。これを平滑化で隠さず採取する。

## タグ検出とSLAMの分離（schema12）

①では検出できる距離で②が無反応という実機報告を受け、directモードの画像取得・Worker投入をSLAM NORMALの条件から分離した。LIMITEDへの遷移でも独立検出jobはキャンセルしない。従来のstrategy=fusionは旧条件を維持する。

②directのタグ位置推定は①と同じ`reduceTagLocalization`を呼ぶ。ID 0・同じ黒境界実寸・同じKを用い、重複ID・姿勢曖昧・再投影2px超過等を①と同じ条件で棄却する。②独自の最小辺8px制限・共通ボード姿勢推定を使用しない。検出器・受け渡す原寸画像・500msの観測期限は両者で共有する。ただしSLAM有効による処理負荷やSDK映像の実条件が同じという保証はない。

有効なSDK姿勢がなくても、タグからの会場カメラ姿勢とマーカー相対姿勢を計算する。画面には検出に使用した同一撮影画像へ軸を描く専用パネルを表示し、未検出／姿勢曖昧／SLAM待ち／外れ値保留を区別する。SDK姿勢がないときはライブの3D空間へ対応づけられないため、過去のSDK姿勢やidentityを代用しない。タグ単独の画像表示とライブ背景の時刻は異なると明示する。

NORMALかつ有効な同フレームSDK姿勢があれば、それを添えてtag-authoritativeへ渡す。位置推定を①と共通化しても、取得時刻の古さ・SLAM復帰・既存外れ値ゲートによってライブの会場対応更新は保留され得る。タグ単独の画像上の位置推定と、会場↔SDK対応の採否を別のログ項目にした。

### JSON出力

「JSONログを保存」を診断折りたたみの外に配置した。開始前・実行中・停止後に保存可能。ファイル名は`audience-anchor-tracking-log.json`。schemaVersion 12で、次を出力する。

- `tagLocalization`: 最終のタグ単独推定（停止/reset後は未推定へ戻る）。
- `tagStatistics`: component-lifetimeの配信画像数・ID0検出数・タグ位置推定成功数・SDK姿勢なしの数・会場対応採用数とタグ推定の理由別件数。resetをまたいだ通算であり、固有センサー画像数やSDK全フレーム数ではない。
- `fiducial.frame.tagLocalization`: 各フレームのタグ相対姿勢・会場カメラ姿勢・再投影誤差・不採用理由。SDK姿勢がnullでも記録する。
- `sdkBinding` / `adoptionReason`: 取得時SDK姿勢の有無と、会場対応を採用・保留した理由。姿勢がなければ`sdk-pose-unavailable`。
- 従来の生検出角・検出器時間・入力寸法・K・取得時SDK姿勢・same-frame比較・fusionState・sdk.pose・計測集計・リング欠落件数を維持する。画像画素そのものはJSONへ含めない。

SDK姿勢がnullならcomparisonのSDK予測もnullとなるが、tagLocalizationは残る。停止後もフレーム明細と通算数は保持する。リング上限で過去明細は欠落し得るため、短い試行ごとに保存する。

## SDK追跡状態の診断（schema13）

schema12実機ログではタグ位置185/214成功に対し、アプリ追跡状態は全件LIMITED、SDK対応更新0だった。一方sdk.poseに355/357の数値姿勢が存在した。生の状態値を保存しておらず、SDK自身のLIMITEDと、アプリの初期LIMITED値が残るケースを区別できなかった。元ログの先頭文字を除去して解析したが、私有ファイル本体を変更・リポジトリへ保存していない。

schema13では次を記録する。状態の採用条件や補間・位置の採用処理は変更しない。数値姿勢の存在だけでNORMALへ強制しない。

| 項目                                      | 内容                                                                                                                                                                                   |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `sdk.tracking.raw`                        | 最大毎秒のpipeline状態。sessionId、callbackAtMs、reality有無、SDK状態・理由の生値/型/キー有無、解釈、実際にアプリが適用した状態                                                        |
| `sdk.tracking.raw-change`                 | 値・型・理由等が変わった時の同じ証拠。初回も保存する                                                                                                                                   |
| `sdk.tracking.event`                      | `reality.trackingstatus`イベントのstatus/reason/trackingStatus/trackingReason、detail型とキー一覧、sessionId、callback時刻、starting/running。イベントによって追跡採用状態を変更しない |
| `sdk.pose.rawTracking`                    | 姿勢サンプルと同じcallbackでの状態・理由                                                                                                                                               |
| `fiducial.frame.rawTracking`              | 検出画像取得時点の状態・理由。captureMetadata.trackingInputにも保存                                                                                                                    |
| `fiducial.frame.sdkPoseAttachment`        | NORMAL文字列条件の成否、位置/回転の有無、有効な数値姿勢か、実際に添付したかと理由。captureMetadataにも保存                                                                             |
| `measurementSnapshot.trackingDiagnostics` | adapter-lifetimeの全update数、イベント数、状態型と解釈ごとの件数、最後のupdate/event。停止・再開後も保持する                                                                           |

値の記録は欠測とnullを区別する。例えばキーなしはpresent=false/type=undefined/value=null、明示的undefinedはpresent=true/type=undefined/value=null、数値2はpresent=true/type=number/value=2。NORMAL/LIMITED以外の型・文字列を独自の状態定数へ変換しない。非有限数は文字列、文字列は最大512文字、オブジェクトは型と最大16キーの一覧とする。SDK内部オブジェクトやrealityTextureを丸ごとシリアライズしない。

毎秒サンプルは検出/SDK姿勢と同じサンプル用リング、変化とイベントは遷移用リングへ記録する。上限による欠落は従来のdroppedSamples/droppedTransitionsで確認する。全update集計はリングが欠けても残るが、全生値の履歴を保証するものではない。

確認手順は、明るく模様のある壁や机を映して起動し、ゆっくり動かした後タグを10秒ほど映し、「JSONログを保存」。rawのstatusとappliedTrackingStatusを比較し、欠測/型不一致/SDKのLIMITEDを区別する。eventでNORMALが出てpipelineが欠測なら、通知イベントを採用する設計が必要か別途検討する。新ログ確認前に原因を断定しない。

軽い一時スクリプトで、起動完了前のイベント、欠測/null/数値状態、生値のJSON保持、数値をNORMALへ変換しないこと、全update集計、停止済みセッションのcallback除外を確認した。スクリプトは削除し、回帰テストは追加・実行していない。

schema13の型検査・lint・本番ビルドは成功。公開HTTPSのentry JSとローカル成果物のSHA-256一致を確認。実機の新しい状態ログは未取得で、SDK追跡状態の原因は未確定。回帰テスト・全体品質ゲートは軽いデバッグの指定に従い未実行。git status・差分・ステージ済差分を確認し、コミット・pushなし。
