# Audience：マーカー検出から会場位置保持までの再設計

> 2026-10-22 PoC完了：ユーザーが現構成の精度を承認したため、追跡方式の再選定は終了する。AprilTag即時確定＋SDK／SLAM保持＋距離別の表示小揺れ補正を採用。以下は再設計時の検討履歴として扱い、未実施の比較・試験をWebアプリ開発の前提にはしない。[採用記録](../experiments/audience-apriltag-adopted.md)と[Webアプリ開発計画](./audience-web-app-plan.md)を参照する。

- 更新日: 2026-10-20
- 状態: 設計提案。方式の採用・新実装・精度達成を示す文書ではない。
- 確認済み要件: 初回認識も7m先から行うことを目標とし、最遠7m、表示位置のずれ約10cm、マーカーが見えない状態で5〜10分保持。8th Wall・AprilTagを含め再選定してよい。
- 設置寸法: ユーザー指定は5枚全体で50×70cm。幅50cm・高さ70cmの平面ボードとして設計する。各タグが50〜70cmという以前の仮定を置き換える。黒い検出境界と白い余白は別に管理する。
- 次の評価方針: 実際の高解像度入力の確認→元画素ROI→カメラ較正→5枚の距離・姿勢一括推定→確定後の継続補正の順に評価する。単一タグの連続補正は2026-10-21に実装した。5枚ボード・ROI・物理較正は未実装。[取得経路の確認記録](../experiments/audience-high-resolution-investigation.md)を参照する。
- 継続する製品方針: 会場の観客がスマートフォンから参加。ログインなしでルームIDを入力する。Unframeは無償。
- 対象: 検出、メートル単位の自己位置、移動追跡、会場座標との対応、描画、再位置合わせ。ライブ同期は別の責務とする。

## 1. 推奨する判断

既存の「検出できたらSLAMへ原点を渡す」実装の延長で精度を調整せず、次の三つを独立に評価する。

1. **会場基準の自己位置**: 既知の物体とカメラ較正から、その撮影時点の端末位置・向きを求める。
2. **移動追跡**: 会場原点を知らなくても、端末の移動・回転とその信頼性を求める。
3. **会場位置の保持**: 両者の座標・尺度・時刻を対応させ、観測が途切れても要求誤差内で表示する。必要なら会場基準を再観測して再位置合わせする。

AprilTagは1の候補であり、タグが見えない間の移動を単独で計測する機能ではない。SLAMのNORMALや固定した行列も3の精度保証ではない。まず独立試験に合格する実装・SDKを選び、その後に統合する。

ブラウザ継続を第一候補とするが、7m・約10cm・遮蔽10分を現行SDKで達成できるという根拠はない。会場内の既知の参照物を再観測できる構成も評価する。ただし、人工マーカーや測量済み会場基準を再観測しない10分の試験は、再観測できる試験と分けて合格させる。通常のSLAMが使う自然特徴の観測は許可する。「完全遮蔽」は以降もこの会場基準の遮蔽を意味する。再観測で直ったことを、その前の保持成功には数えない。

## 2. 要求を試験可能にする

| 項目         | 現在の要件／扱い                                                                                                |
| ------------ | --------------------------------------------------------------------------------------------------------------- |
| 最遠距離     | マーカーから観客まで7m。初回認識も7m先から行うことを目標とする。読取と精度確定の距離を別に記録する              |
| 表示位置     | 約10cm以内。提案基準は会場内の複数の表示基準点について実物との3D距離で評価する                                  |
| 遮蔽中の保持 | 5分と10分を試験。可視状態・再観測あり・完全遮蔽を分ける                                                         |
| マーカー寸法 | 5枚全体で50×70cm。各タグの寸法・配置は下記の初期案で評価する。現在の単一タグ15cm設定は5枚ボードとは別の統合実験 |
| 対象端末     | 既存実測はiPhone 13 / Safari。OS・ブラウザ版・カメラ・解像度を試験ごとに固定する。Androidは別評価               |
| 未確定       | 各タグの黒境界・余白寸法の最終値。画面／紙、会場照度、観客の移動範囲、許容非表示時間、角度誤差・遅延の基準      |

10cmという値をP95だけに適用するか、最大誤差にも適用するかは未決定。評価ではP50・P95・最大値・要求内にいた時間率をすべて出し、結果を見て合格定義を緩めない。上表の「提案基準」はまだ承認済みの詳細仕様ではない。

位置だけでなく角度と尺度が遠いコンテンツのずれを増幅する。小角度近似では、原点の並進誤差に、原点から表示点までの距離×角度誤差と、同距離×相対尺度誤差が加わる。7m先で1度は約12.2cmに相当する。したがって、端末の位置誤差だけ10cm以内でも表示点が10cm以内になるとは限らない。誤差予算は表示点で割り当てる。

初回認識は7mで評価する。近距離で認識してから離れる試験だけでは、この要件を満たしたことにしない。

現ログの入力に見られる焦点距離約716pxを例に、正面のタグ幅は概算 `f × L / Z` で次のようになる。寸法Lは白い余白を含まない検出境界である。

| 黒い検出境界の一辺 | 7mでの概算幅 |
| ------------------ | ------------ |
| 15cm（現PoC）      | 約15px       |
| 40cm               | 約41px       |
| 50cm               | 約51px       |
| 60cm               | 約61px       |

これは幾何の例で、検出限界・姿勢精度の実測値ではない。解像度・レンズ・斜視・ブレで変わる。タグが大きくなれば同じ距離で使える画素数は増えるが、約10cmの表示精度や不可視10分の保持を保証しない。単純な正面モデルでも50cmタグの幅51pxに対する1pxの系統的な幅誤差は、7mの奥行きで約14cmに相当する。サブピクセル角推定や複数点の効果はあるため、これは誤差下限ではなく較正・角精度を検証する理由として扱う。

次の比較対象は、全体50×70cmの5枚ボードとする。従来の大判単一タグは比較用の既存実験として区別する。小さいタグを5枚に分けても各タグの識別画素数は増えない。一方、全体へ広く配置した検出角を同時に使うことで、距離・向きの推定を改善できるかを評価する。枚数の増加だけで改善したと判断しない。

### 50×70cm・5枚ボードの初期配置案

四隅と中央に異なるIDを配置する。原点はボード中央、X右、Y上、Z正面。全タグを同じ向き・同じ平面Z=0に固定する。次は設置可能性を確認する初期案であり、各タグ14cmという寸法までユーザーが指定したものではない。

| ID        | 中心X | 中心Y | 黒い検出境界の一辺 |
| --------- | ----- | ----- | ------------------ |
| 0（中央） | 0cm   | 0cm   | 14cm               |
| 1（左上） | -14cm | +24cm | 14cm               |
| 2（右上） | +14cm | +24cm | 14cm               |
| 3（右下） | +14cm | -24cm | 14cm               |
| 4（左下） | -14cm | -24cm | 14cm               |

各タグに片側3.5cmの白い余白を確保すると1枚の占有範囲は21×21cm。上記配置の占有外接矩形は49×69cmで、50×70cm内に収まる。ボードの寸法だけでなく、黒境界の幅・高さ、IDごとの中心位置、平面性も実測する。設置後に動くタグは既知配置として使わない。

焦点距離716pxの例では、14cmの黒境界は7mで約14.3pxとなる。これは現行の大判単一タグより小さく、7mでIDと角を安定取得できるかは未検証。全体へ広げた角の基線が役立つのは、必要なタグを識別できた場合である。7mで不足すれば、実入力解像度、処理解像度、辞書・検出実装、寸法配分を比較する。低解像度画像の拡大や、遠距離で検出できないタグの追加で解決したとは扱わない。

### 連続観測による補正の評価方針

1. 見えたタグの登録済み頂点を共通の会場座標へ変換し、最大20頂点から一つのカメラ位置・向きを推定する。独立した距離5個の単純平均にはしない。未登録ID・重複ID・外れた角／タグを除外する。
2. 初期確定後も検出を継続する。可視枚数だけで品質を判定せず、画素数・角の広がり・候補の曖昧性・タグ間の整合性から観測の採否を決める。5枚が常時見えることを必須にしない。
3. 採用した自己位置と撮影時点に対応する追跡姿勢から、会場と追跡地図の対応を更新する。観測間は追跡器を使う。SDK尺度が未知なら継続する対応観測から尺度も検証し、一枚のボード姿勢だけでSDK尺度が確定したとは扱わない。
4. 単発外れ値は補正に使わず、整合する観測を確認する。平滑化は表示の揺れを制御するために用い、距離の偏りや時刻不整合を隠す目的には使わない。大きい差は正しい再位置合わせか誤観測かを判定してから適用する。
5. マーカーが見えない間の保持試験は別に行う。連続補正で精度が上がっても、不可視5〜10分の保持成功の代わりにはならない。

現在の`mode=anchor`は単一タグ15cmの継続補正とSLAM追跡を統合している。仮位置・確定・再確認を分離し、尺度は初期較正後に固定する。5枚同時推定・ROI・物理較正は未実装であり、[連続融合の実装記録](../experiments/audience-continuous-fusion.md)で範囲と限界を確認する。

過去ログ3〜5のSDK開始時video報告は768×1024px、検出入力は主に566×960pxだった。960px上限の解除だけで実情報が2倍・4倍になるとは仮定しない。まず[高解像度取得の確認手順](../experiments/audience-high-resolution-investigation.md)に従い、元映像と各テクスチャ・canvas・検出入力の寸法を区別する。入力解像度を上げる案は、実際のカメラ解像度・処理負荷・FPS・発熱を含めて比較する。低解像度画像の拡大を情報量の増加と数えない。7mで「IDが読める」と「会場基準の自己位置が誤差予算内で確定する」を別の合格項目にする。

## 3. これまでに分かったことと、まだ分からないこと

### 確認した実装上の問題

- SDKのcanvas解像度とCSS寸法の対応により背景と検出枠がずれる問題があった。
- 姿勢最適化が不適切な局所解へ収束する実例があり、別の初期値で再投影誤差が改善した。すべてを平面タグ固有の曖昧性のせいにはできない。
- SDKがNORMALのまま、アプリ側の否定観測判定で原点を破棄した区間があった。SDKが自己位置を失った証拠とは区別する。
- 遅延した検出結果の枠を現在のカメラ映像へ重ねると、動作時の表示位置が対応しない。

これらの修正は必要だが、要求精度を実証するものではない。

### 既存ログから断定しないこと

- 8.6cm等の推定移動幅はPnPの出力であり、実測した端末移動距離ではない。「利用者が十分動かなかった」とは断定できない。
- 複数回の較正尺度のばらつきは、SDK尺度が同量変動した証拠ではない。PnP・時刻・較正誤差も含む。
- 再投影誤差が小さくても、実際の距離・向きが正しいとは限らない。
- 再観測との差約17cmという過去の指標は内部推定値間の差であり、真値に対する位置誤差ではない。
- 原点行列を維持した時間や非表示を増やした結果を、追跡精度の改善に置き換えない。

外部の基準計測、実機の内部パラメータ・歪みの妥当性、撮影とSDK姿勢の時間対応、長時間・7mでの精度は未検証である。既存の合成テストは数学・契約・回帰の検証として残す。

## 4. データと座標の契約

`T_A_B`はB座標をA座標へ変換する剛体変換とする。距離はメートル、回転の表現・軸・角順序は境界で明記する。

- 会場: `V`。設置時に決定し、端末の再スキャンで変更しない。
- マーカー: `M`。検出境界の実寸と、設置済みの `T_V_M` を設定する。
- 撮影カメラ: `C`。コンピュータビジョン側の軸を定義する。
- 追跡地図: `W`。SDKの原点・単位・再初期化の扱いを明示する。

タグ観測 `T_C_M` から `T_V_C = T_V_M × inverse(T_C_M)` を求める。OpenCVのカメラ軸からThree.jsへ変換する場合、同じタグ座標を維持するならカメラ側の基底変換は `diag(1,-1,-1)`。ソルバーの軸定義を確認し、既存POSITの変換を他のソルバーへそのまま移植しない。

### フレーム契約

| データ   | 必須の扱い                                                                                       |
| -------- | ------------------------------------------------------------------------------------------------ |
| 識別     | frameId、取得元、画素寸法、処理寸法                                                              |
| 時刻     | clock domain、撮影時刻または不明、取得・処理完了時刻。撮影時刻が不明なら時間誤差の上限を測定する |
| 画素変換 | crop、resize、回転、反転、映像から表示への変換                                                   |
| カメラ   | K、歪み係数または補正済みという宣言、較正ID・適用条件                                            |
| 追跡     | 同時刻の `T_W_C`、単位、状態、地図の識別／変更通知の取得可否                                     |
| 品質     | 欠測・古さ・取得不能を明示する。未知の共分散をゼロで埋めない                                     |

callbackの `performance.now()` を撮影時刻と呼ばない。非同期結果に最新のカメラ姿勢を組み合わせない。SDKから必要な値が得られなければ「不明」として実測または選定の制約にする。アプリのキャンセル用epochをSDK地図のepochとみなさない。

SDKの描画用4×4投影行列だけで、物理カメラのK・歪み・撮影時刻まで較正済みとは扱わない。画素のアフィン変換に応じてKを更新する。歪み補正は別に扱い、補正済み画素へ二重に補正しない。

## 5. 責務の分離

| 境界                    | 入力→出力                                           | 担当しないこと             |
| ----------------------- | --------------------------------------------------- | -------------------------- |
| CameraSource            | カメラ→上記フレーム契約                             | 会場原点の決定             |
| TagDetector             | 同一画素→ID・順序付き角・検出品質                   | SDKへの原点設定            |
| MetricLocalizer         | 角・K・実寸・既知配置→会場自己位置の候補群と品質    | マーカー不可視時の移動追跡 |
| MotionTracker           | センサー／SDK→時刻付き相対姿勢・単位・追跡状態      | 会場の定義                 |
| VenueAlignmentEstimator | 対応観測→会場と追跡地図の変換・尺度・適合度         | 描画可否のUI判断           |
| AnchorManager           | 推定・追跡状態→使用する対応、再位置合わせ、表示方針 | 欠測を成功として隠すこと   |
| Renderer                | 時刻の対応したカメラ・会場オブジェクト→描画         | 推定器の状態更新           |

これらは契約上の境界であり、最初から全てを新クラス・共通packageにする指示ではない。Audience内で状態と純粋計算を分け、所有範囲に閉じて実装する。

### 自己位置の推定

単一タグ・一枚の画像でも、既知実寸と適切なKがあれば姿勢を推定できる。SLAMの尺度合わせに使った「10cm移動」はAprilTagの要件ではない。

平面姿勢は候補を複数保持し、公式AprilTagの姿勢推定やOpenCVのIPPE_SQUARE等を参照実装として比較する。ピクセル再投影誤差とAprilTagの物体空間誤差を同じ単位として比較しない。候補間の判別不能は不確かさとして返す。静止した一枚の試験では時間的な前姿勢を使わず、最適化失敗と曖昧性を切り分ける。

複数タグは設置位置・寸法の誤差も持つ。平面上に増やすだけで全条件の曖昧性が消えるとは仮定しない。大きい基線のボード、異なる向きの参照面、会場内の既知配置を、設置の容易さと一緒に比較する。

### 移動追跡と尺度

メートル単位が検証済みの追跡なら会場対応はSE(3)、未知尺度ならSim(3)とする。後者は `p_V_C = s R p_W_C + t`、`R_V_C = R R_W_C`。一枚の姿勢だけでは未知尺度は確定できない。

固定の観測数や「10cm動いた」だけを尺度確定の根拠にしない。運動と回転の情報量、尺度のばらつき、独立した後続観測の予測誤差で判定する。SDKの内部地図変更・尺度変更の有無と検知方法も試験する。

統合推定の候補は、PnP候補を初期値として、複数時刻のタグ角とSDK姿勢から共通の会場対応を直接最適化する方式。目的関数は既知の会場頂点を各カメラへ投影したピクセル残差にロバスト損失をかける。SDK姿勢にも誤差があり、同じ映像に由来する相関があるため、独立で完全な真値とは扱わない。Kや時間対応の誤りを最適化で吸収しない。カメラ契約と独立精度を確認してから採用判断する。

### 保持・再位置合わせ

追跡状態、会場対応の信頼性、観測の鮮度、描画可否を別々に持つ。タグの一回の欠測・外れ値で会場定義を消さず、追跡喪失時に古いカメラ姿勢を現在値として使わない。タグ専用表示でも観測の有効期限を持つ。

地図の連続性が確認できる間は会場対応を保持する。再観測は候補の整合確認を経て採用し、大差を毎フレームの補間で隠さない。対応が不明になった場合は不確実な表示を止めて再位置合わせへ進む。この非表示は精度成功ではなく可用性低下として計測する。SDKの地図リセットが通知されない場合は、アプリから安全に判別できるかが選定条件になる。

| ARKitのネイティブ／App Clip | カメラ・センサー・地図への契約を比較する基準     | 純粋なSafari閲覧からの製品要件変更。実際の精度は別途測定     |

iPhone Safariで標準WebXR immersive-arやARKitのanchorがそのまま使えるとは仮定しない。visionOSのWebXR対応とiPhoneを混同しない。製品が無償でもSDKが必ず無償である必要があるとは解釈しない。費用・ライセンス・CORS・ドメイン・表記・通信は候補の技術評価と並行して確認する。

AprilTagとArUcoは残すが、現行の古いWASM移植・ファミリーを最終選定としない。公式実装との一致、角精度、誤検出、実機負荷を比較して版を固定する。独自VIOの新規開発や、単なる平滑化フィルターの追加を最初の解決策にしない。

## 7. 実験と合格の順序

各試験の前に試験条件・許容誤差・評価区間を記録する。最終表示の約10cmを各段の誤差予算へ分ける数値は未決定であり、下表の距離等は試験案である。

| 段階                  | 試験                                                                                                     | 次へ進む条件                                                                       |
| --------------------- | -------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| G0 基準計測           | 実寸・設置位置、カメラ光学中心・向き、画素変換、K・歪みを確認                                            | 評価基準自体の誤差が目標より十分小さい。目安として目標の1/3以下を提案              |
| G1 検出               | 同一画像群で1/3/5/7m・角度・照明・ブレ・紙／画面を比較。次の主対象は50×70cmの5枚ボード                   | 正検出・誤検出・未検出、角誤差、処理時間と入力棄却数が測れる                       |
| G2 単フレーム自己位置 | 近距離の0.3/0.5/0.75/1mで切り分けた後、設置可能な大判タグで3/5/7m、角度0/15/30度等の既知位置から反復撮影 | メートル・角度の偏り、揺れ、反転、候補判別を測定し誤差予算内。参照ソルバーとも比較 |
| G3 移動追跡単独       | 既知経路で静止・平行移動・回転・往復、最大7m                                                             | タグ補正なしの尺度・角度・帰還誤差、地図変更、追跡喪失を測れる                     |
| G4 座標・時刻の結合   | タグ可視の移動で独立観測と追跡を対応                                                                     | 合成画像だけでなく実機で符号・尺度・遅延の系統誤差が予算内                         |
| G5 不可視保持         | 初期化後タグを外し、静止／回転／歩行を5分・10分、最遠7mで評価                                            | 複数表示点のずれ・時間率・最大値が合意基準内。復帰後の残差だけでは判定しない       |
| G6 再位置合わせ       | 部分遮蔽、誤検出、退出再入場、画面復帰、地図リセット                                                     | 誤った会場対応を採用せず、復帰時間と表示ジャンプが合意基準内                       |

G2の近距離条件は最初の切り分け用である。5枚ボードでは全体が収まる距離へ調整する。7mからの初回認識を目標として、G1・G2の7mと中間距離の寸法別試験を必須にする。7mから静止した状態で認識を開始し、初検出までの時間・姿勢確定までの時間・成功率・誤確定率を記録する。姿勢取得に平行移動が必要になる設計では、その操作条件を別途評価し、単フレームで取得できた結果と混ぜない。

止まった位置の真値は治具・測量で比較できるが、連続移動中の誤差には外部追跡等の時間同期した基準が必要。物差しだけで連続6DoF精度を保証しない。まず静止地点で偏りを切り分け、必要なら外部カメラ／モーションキャプチャを使う。

評価条件は端末・OS・解像度・実装版・照度・マーカー配置・移動経路・温度・FPS・検出負荷を含む。マーカーとコンテンツの距離を変え、近い検証箱だけで遠い表示の精度を代表させない。登壇側との会場座標の測量誤差も最終統合で加算する。

ログには全取得数、処理対象数、busy／間隔制限／同一フレーム／K不足等の除外数、観測齢、検出・描画遅延、再初期化、表示中断を記録する。成功フレームだけを分母にしない。現ログのリングバッファ上限で欠けた区間を全セッションと呼ばない。

検出器を再評価するには画素データが必要になる。開発者の明示的な試験用データをローカル収集する設計とし、観客の映像を自動保存・送信する機能は追加しない。既存の個人ログをそのままリポジトリに取り込まない。

## 8. 現在のPoCと移行

現コードは、SDKのworld trackingを無効にした単フレーム自己位置確認`mode=tag`と、継続補正＋SLAM追跡を行う既定`mode=anchor`を持つ。どちらも単一ID 0・黒外周15cmを既定にする。anchorはSDK尺度を複数観測で較正し、確定後は尺度固定の小補正を継続する。弱い単一候補の整合は仮位置、複数の強観測の整合は確定とする。複数姿勢候補だけでは初期確定せず、LIMITED復帰後も強観測で再確認する。これは要求精度を実証した製品ではなく、統合挙動を評価するPoCである。

再利用するものは、検出用入力、実寸設定・印刷、Worker接続、ライセンス配信、座標の純粋計算テスト、同一画素比較、合成ラボ。カメラ契約は実測して再確認する。現行の独自POSIT探索、移動量固定閾値、内部残差を中心とした合否判定は、そのまま最終設計へ採用しない。

現tagモードは大判プロファイル、同一画像での距離・画素数の測定、取得除外集計と観測期限を実装した。R0としてtag／anchorのschemaVersion 7にvideo・frameStart camera texture・canvas・予定／実readbackの寸法と出自を記録し、停止・再開後も証拠を保存できる。tagの新ログでSDK videoとcamera feed textureがともに768×1024pxと確認できた。anchorとの比較・最大取得能力・距離精度は未確認。サイズ通知の未知項目が予定寸法を壊す計測不具合は再現テストで修正した。詳細は[取得経路の記録](../experiments/audience-high-resolution-investigation.md)を参照する。露光時刻の確証は未完了。R0は当時のschema7計測記録である。現在はtagがschema8、anchorがschema9で、原寸入力と新しい連続補正を記録する。会場対応を保持・補正してもSDK地図の安定性や実物との精度は保証しない。新実装による実機評価は未完了である。

進め方は、要求の残項目を確定し、G0〜G2の計測環境と参照ソルバーを作り、G3で追跡候補を比較し、合格した組合せだけG4〜G6へ進める。合成で失敗を再現できる計算・状態にはRed→Green→Refactorを適用する。実機精度は実験として記録する。再設計後の最初の実装として、G0〜G2向けの[大判タグ計測基盤](../experiments/audience-large-tag-protocol.md)を追加した。参照ソルバーへの交換、新SDK導入、実機精度の合否判定はまだ実施していない。
