# オーディエンス向けWeb XR 設計・開発計画

- 作成日: 2026-10-20
- 状態: 設計案。Audienceアプリケーションは未実装。
- 実装調査の基準: 作成時のローカル `origin/main`、`923e64e1`。
- 製品の前提: Unframeは無償。会場の観客がスマートフォンで、登壇者と同じ物理空間・進行を視聴する。
- 技術方針: 8th Wall + Image Targets + SLAM + Three.js。

この文書は開発の目的、暫定設計、作業順序、受け入れ条件を記録する。将来の機能を既存機能として扱わない。実装時には対象ブランチのコードと契約を再確認し、確定した仕様を所有アプリのREADME・設計文書へ反映する。

## 1. ブランチ運用

```text
main
  └─ webXR/audience              統合ブランチ
       ├─ webXR/design           設計・開発計画
       ├─ webXR/tracking-poc     画像認識・位置合わせ・追跡
       ├─ webXR/rendering        既存成果物の表示
       └─ webXR/realtime         視聴者としてのライブ接続
```

`webXR/`で統一し、`webXR/audience`を今回の開発全体の統合先とする。各作業ブランチは、その作業開始時点の更新済み統合ブランチから作り、PRのbaseを統合ブランチにする。上図は作業候補であり、すべてのブランチを先に作成する指示ではない。

最初は `webXR/design` で本計画を作成し、取り込み後に位置合わせPoCへ進む。後続作業は必要な先行変更が統合されてから開始する。並行作業が必要な場合はworktreeも分ける。

mainの変更は統合ブランチへ定期的に取り込み、各作業ブランチを更新する。実装途中の機能を長期間まとめ続けず、独立して検証できる区切りでmain向けPRを作る。最初の区切りは位置合わせPoCの検証結果とし、mainへの取り込み可否はその結果で判断する。公開PRの履歴を無断で書き換えない。

既存のUnity等の未コミット変更は取り込まない。main上にない機能が必要になった場合は依存関係として記録し、所有ブランチでの統合を待つか、必要な変更だけを明示して取り込む。コミット・push・PR作成は個別の依頼時に実施する。

## 2. 目的と初期範囲

観客はログイン・アカウント登録なしでAudienceサイトを開き、ルームIDを入力して参加する。参加後にカメラ等の権限を許可し、会場の固定画像を認識すると、登壇者と同じ位置にプレゼンテーションが見える。画像を視野から外した後は各端末のSLAMで追跡する。進行はサーバーが保持する視聴者向け状態へ同期する。

初期対象はiOS SafariとAndroid Chrome。対象OS・端末・ブラウザの具体的な範囲はPoCで確定する。ヘッドセット向けブラウザ、遠隔地への配置、編集・登壇操作、全表現への対応は初期範囲に含めない。

基本の参加導線はサイトへのアクセスとルームID入力とする。参加用QRを設ける場合も補助導線とし、位置合わせ用Image Targetと区別する。QRの読取成功を空間較正成功として扱わない。観客の再スキャンはその観客のローカル座標変換だけを更新し、セッション全体の原点を変更しない。

## 3. 技術選定と確認事項

SLAMにはDistributed Engine Binaryを利用する。MIT版のImage Targetsだけでは今回のWorld Tracking要件を満たさない。バイナリはバージョンを固定し、必要な実行ファイルとライセンス表記を配信する。Three.jsの対応バージョンと初期化方法はPoCで確認し、依存関係を固定する。

Unframeが無償であることを前提とし、有償製品とは扱わない。ただしバイナリの利用・配布・表示条件は無償利用でも適用されるため、採用する配布物のLICENSEを確認する。SLAMのソースを修正できない点と、将来のブラウザ更新への追従を技術上の制約として記録する。

HTTPS、カメラ・センサー権限、WebAssembly、WebGLの利用条件を実機で確認する。Web XRという名称はブラウザでのXR体験を示し、初期実装で標準WebXR Device APIを必須とすることは意味しない。

配信・表記要件と実機検証の開始条件は、[Distributed Engine Binaryの導入・配信要件](./audience-web-xr-engine-requirements.md)に記録する。同一origin配信を初期方針とし、公式資料の確認と採用バージョンの実機起動確認を区別する。

## 5. 位置合わせの契約

Presentation座標は既存契約のメートル・右手系・+Y上・-Z前に従う。Unity専用の座標反転をThree.jsへコピーしない。

`T_A_B`をB座標からA座標への変換とする。Wを端末のSLAM空間、Mを画像ターゲット、Vを会場、PをPresentationとすると、描画用の変換は次で求める。

```text
T_W_P = T_W_M × inverse(T_V_M) × T_V_P
```

画像観測で得られる `T_W_M` はSDKの軸とスケールを正規化してから使う。実寸・Absolute Scaleの成立を検証し、単位が合っていない観測を剛体変換として受理しない。

共有する情報の候補は、会場配置ID・バージョン、ターゲットID・画像ハッシュ・実寸、会場内の位置と回転、Presentationの会場内配置である。既存の原点・publication契約との関係を先に確認し、配置情報の所有先・取得API・失効条件を確定してから共有schemaを追加する。

Quest側のArUcoとWeb側の画像は、同じ会場座標に対応付ける。両者を同じ固定ボードに載せる案を検証する。会場位置が未知の手持ち画像は共有原点として扱わない。

較正は探索・安定確認・較正済み・再較正要求の状態を持つ。複数観測の安定性を確認し、外れ値を除外する。画像喪失とSLAM喪失を区別し、SLAM継続時は画像喪失だけで即座に非表示にしない。原点リセット・SDK再起動・会場配置変更時は較正を失効させる。再認識時の補正方針と閾値は測定結果から決める。

## 6. 既存資産と追加実装

調査の根拠:

- [Presentation契約](../../packages/contracts/src/presentation/definition.ts)
- [Core公開API](../../packages/unframe-core/src/index.ts)
- [ビルド時Web rendererの責務](../../packages/unframe-renderer-web/ARCHITECTURE.md)
- [Realtimeの双方向stream契約](../../packages/contracts/proto/unframe/realtime/realtime.proto)
- [参加・bootstrap API](../../app/server/control-plane/src/modules/sessions/routes.ts)
- [端末能力プロファイル](../../app/server/control-plane/src/modules/publications/capability.ts)

既存の公開物・配信契約、素材、整合性検証、タイムライン補間を利用する。`unframe-renderer-web`はビルド時に画像を生成する仕組みであり、視聴用Three.js rendererとして組み込まない。既存WebのUnity PreviewをThree.js実装済みと扱わない。

初期表示は焼き込みPNG surfaceに限定し、寸法・透過・レイヤーを再現する。Web用capability profileを追加し、未対応表現は配信選択時に明示的に拒否する。GLB・動画・Native UI相当の対応は、各契約・端末制約を確認した別の追加作業とする。

Realtimeは現在gRPC bidi契約である。ブラウザ向けWebSocket transport adapterを第一候補とし、既存の認証・assignment fencing・viewer投影とsession logicを利用する。通常のgRPC-Webだけでbidi接続できるとは仮定しない。Control/Stateの対応、順序、ACK、backpressure、再接続、snapshot/replayの適用を契約として定める。

視聴専用でもhandshake・ready・ACK等の上り通信は必要となる。UIの非表示だけで操作を制限せず、サーバーがviewer権限を検証する。再生は到着したイベント数ではなくauthoritativeな状態・時刻へ合わせ、途中参加と復帰でも現在の進行に追いつく。

参加方針はログイン不要・ルームID入力で確定する。オーディエンスにアカウント登録や既存ログインを要求しない。ルームは既存Sessionに対応し、別のRoomリソースは作らない。

現行join APIは認証identityを要求するため、そのまま利用できるとは扱わない。Control Planeに匿名オーディエンス向けの参加経路を追加し、入力されたルームIDと参加可能なセッション状態を検証して、サーバー側で匿名participantとviewer専用の参加資格を払い出す。クライアントから任意のroleやparticipant IDを指定して権限を取得できないようにする。匿名参加でもRealtimeと素材配信は発行された参加資格で認可し、閲覧範囲を参加ルームへ限定する。

ルームIDを既存join codeに対応付けるか、Session IDと別の公開用識別子にするかは契約設計時に決める。入力UIの名称はルームIDとし、内部Session IDの直接公開や既存join codeとの同一視は先に確定しない。参加資格の有効期限・再接続・再読み込み時の継続方法、参加試行のレート制限を定義し、ログイン画面への誘導で代替しない。

素材URLの期限更新・CORS・キャッシュ・メモリ上限も定義する。

## 7. 開発順序と受け入れ条件

| 順序 | 作業                                   | 次へ進む条件                                                                                             |
| ---- | -------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| 1    | 設計、基準実装と利用条件の確認         | 未決事項と依存関係、検証方法を記録できた                                                                 |
| 2    | ローカルの位置合わせPoC                | 実寸図形が固定位置に表示され、画像を外した追跡と再スキャンを実機で確認できた                             |
| 3    | Questとの会場原点比較                  | 同じ実物位置への表示を測定し、座席範囲と許容誤差を確定できた                                             |
| 4    | 既存PNG公開物の再生                    | サイズ・向き・色・透過・レイヤーと非対応表現の拒否が確認できた                                           |
| 5    | ログイン不要のルームID参加とライブ同期 | アカウントなしの参加、viewer権限、無効ID・参加不可状態の拒否、途中参加、進行、切断復帰、失効を検証できた |
| 6    | 複数台・実会場検証                     | 合意した精度・性能・復帰条件を満たし、制約を文書化できた                                                 |

各作業は探索→Red→Green→Refactorで進める。座標変換、状態遷移、順序・重複処理、失効、権限制約に振る舞いのテストを追加する。カメラ追跡や見え方は実機評価を必要とし、モックの成功だけで合格としない。

SDK導入時にバージョンと端末一覧を記録し、ターゲット寸法・距離・角度・照度を揃えて測定する。初期検証では座席ごとの認識成功率、較正所要時間、位置・角度誤差、数分後のドリフト、FPS、発熱、進行遅延、復帰時間を残す。数値の合格基準は会場の寸法・視聴距離を決めた後、測定前に合意する。

対象領域のcheckを先に実行し、コード変更完了時は `nix run .#check` を実行する。Nix変更時は `nix flake check`、Unity挙動変更時はEditorテストも実行する。新Audienceのcheck/test/build入口をscriptsとflakeへ接続する。コマンドの未実行・失敗と代替検証を記録し、品質コマンドの前後で差分を確認する。
