## 1. ブランチ運用

```text
main
  └─ webXR/audience              統合ブランチ
       ├─ webXR/design           設計・開発計画
       ├─ webXR/tracking-poc     画像認識・位置合わせ・追跡
       ├─ webXR/rendering        既存成果物の表示
       └─ webXR/realtime         視聴者としてのライブ接続
```

`webXR/`で統一し、`webXR/audience`を今回の開発全体の統合先とする。各作業ブランチは、その作業開始時点の更新済み統合ブランチから作り、PRのbaseを統合ブランチにする。上図は作業候補であり、すべてのブランチを先に作成する指示ではない。

最初は `webXR/design` で本計画を作成し、取り込み後に位置合わせPoCへ進む。後続作業は必要な先行変更が統合されてから開始する。並行作業が必要な場合はworktreeも分ける。

mainの変更は統合ブランチへ定期的に取り込み、各作業ブランチを更新する。実装途中の機能を長期間まとめ続けず、独立して検証できる区切りでmain向けPRを作る。最初の区切りは位置合わせPoCの検証結果とし、mainへの取り込み可否はその結果で判断する。公開PRの履歴を無断で書き換えない。

既存のUnity等の未コミット変更は取り込まない。main上にない機能が必要になった場合は依存関係として記録し、所有ブランチでの統合を待つか、必要な変更だけを明示して取り込む。コミット・push・PR作成は個別の依頼時に実施する。

## 2. 目的と初期範囲

観客はログイン・アカウント登録なしでAudienceサイトを開き、ルームIDを入力して参加する。参加後にカメラ等の権限を許可し、会場の固定マーカーまたはマーカーボードを認識すると、登壇者と同じ位置にプレゼンテーションが見える。マーカーを視野から外した後は各端末のSLAMで追跡し、再観測時に会場座標との整合を検証・補正する。進行はサーバーが保持する視聴者向け状態へ同期する。

初期対象はiOS SafariとAndroid Chrome。対象OS・端末・ブラウザの具体的な範囲はPoCで確定する。ヘッドセット向けブラウザ、遠隔地への配置、編集・登壇操作、全表現への対応は初期範囲に含めない。

基本の参加導線はサイトへのアクセスとルームID入力とする。参加用QRを設ける場合も補助導線とし、位置合わせ用マーカーと区別する。QRの読取成功を空間較正成功として扱わない。観客の再スキャンはその観客のローカル座標変換だけを更新し、セッション全体の原点を変更しない。

## 3. 技術選定と確認事項

SLAMにはDistributed Engine Binaryを利用する。MIT版のImage Targetsだけでは今回のWorld Tracking要件を満たさない。バイナリはバージョンを固定し、必要な実行ファイルとライセンス表記を配信する。Three.jsの対応バージョンと初期化方法はPoCで確認し、依存関係を固定する。

### 3.1. 検出・追跡方式の採用方針

2026-10-20の実機報告では、幅30cmの自然画像の初回認識は約50cmで、認識後の移動で大きなずれが発生した。提供ログには、画像を検出し続けてSLAMがNORMALでも固定原点と後続観測の位置・回転・スケールが大きく乖離する区間がある。検出器の変更だけで画像外のSLAM誤差まで解消したとは扱わない。数値と既存PoCの実験条件は[精度比較の記録](../experiments/audience-tracking-accuracy.md)を参照する。

次の方針で専用マーカー方式へ進む。

1. AprilTag 3とArUcoを、同じカメラ入力・処理解像度・実寸・距離・角度・照明で比較する。第一の比較候補はAprilTag 3とし、iPhone Safariでの優位を事前に決めない。ファミリー・辞書と検出器実装／版を別々に記録する。
2. 選定した検出器で、会場内の既知配置にある複数マーカーを扱う。単一の固定ボードへ複数配置する構成から始め、必要なら会場内へ複数ボードを配置する。同じ面積へ小さいタグを詰め込むことを距離改善とみなさず、個々の実寸と画面内画素数を測る。
3. マーカーの再観測で、会場と端末のSLAM座標の対応を更新する。補正するのは当該端末の描画用変換であり、共有の会場原点や進行状態を動かさない。
4. ChArUcoは角位置・姿勢精度の追加比較候補とする。初回認識距離の優位は仮定せず、AprilTag／ArUcoの比較を先に行う。

AprilTag模様を8th Wall Image Targetsに登録するだけでは、AprilTag専用検出器を使ったことにはならない。専用検出器は別の境界として追加し、8th WallはSLAM・カメラ・描画ループを担う。現在の比較PoCはAprilTag 3のARENA WASM移植とjs-aruco2@2.0.0のArUco JavaScriptを同一Workerで実行する。ファミリーはtag36h11／DICT_4X4_50。実装言語・移植・設定が異なるため、処理時間の差を方式全体の優劣と断定しない。8th Wallに専用検出機能が内蔵されているという意味ではない。

旧Image Targets、画像のみ追従、absolute／responsive／実寸指定の比較UI・生成画像・較正コードは削除する。過去の数値と条件は実験記録へ履歴として残す。失敗時の旧方式への自動代替経路は作らない。両専用検出器への同時入力は比較目的であり、原点には選択した方式のみを採用する。

根拠: [AprilTag公式](https://github.com/AprilRobotics/apriltag)、[AprilTag 3原論文](https://april.eecs.umich.edu/media/media/media/pdfs/krogius2019iros.pdf)、[ArUco Board](https://docs.opencv.org/4.x/db/da9/tutorial_aruco_board_detection.html)、[ChArUco](https://docs.opencv.org/4.x/df/d4a/tutorial_charuco_detection.html)。論文の当時の比較結果を、現行ArUcoや採用端末への性能保証としない。

### 3.2. エンジン・ブラウザの条件

HTTPS、カメラ・センサー権限、WebAssembly、WebGLの利用条件を実機で確認する。Web XRという名称はブラウザでのXR体験を示し、初期実装で標準WebXR Device APIを必須とすることは意味しない。

## 5. 位置合わせの契約

Presentation座標は既存契約のメートル・右手系・+Y上・-Z前に従う。Unity専用の座標反転をThree.jsへコピーしない。

### 5.1. 入力と責務

専用検出器adapterの観測契約には、少なくとも次を持たせる。共有schemaの追加は消費者と配信元を確定した時点で行い、以下を実装済みの型として扱わない。

- フレームID、撮影・処理時刻、映像の解像度、crop・回転の情報。
- 検出器の種類・版、マーカーファミリー／辞書・ID、検出した角の画素座標。
- 正規化したカメラ相対姿勢、使用したマーカー実寸とカメラ内部パラメータの識別情報。
- 検出器が実際に返す品質情報、再投影誤差、姿勢解の曖昧さ・採否理由。異なる検出器のスコアを同じ尺度として比較しない。

カメラ入力は8th Wallの所有する映像から取得し、別のgetUserMediaや描画ループを重複起動しない。公開APIで画素と対応するカメラ姿勢を取得できることを先に実証する。映像の縮小・crop・回転と、姿勢推定に使う内部パラメータの解像度を一致させる。焦点距離・主点・歪み補正の根拠を記録し、未較正の値で精度成立を仮定しない。

検出処理はWorker／WebAssemblyを候補とする。処理中のフレーム数を制限し、古い観測をキューへ蓄積しない。フレームIDと時刻でSLAM姿勢に対応付け、遅延の大きい観測は補正へ使わない。カメラ画素をログへ保存せず、実験条件・姿勢・品質・処理時間を保存する。

### 5.2. 座標・尺度の対応

`T_A_B`をB座標からA座標への剛体変換とする。Wをメートルへ正規化した端末SLAM空間、Cをカメラ、M_iを各マーカー、Vを会場、PをPresentationとする。

```text
T_W_Mi = T_W_C × T_C_Mi
T_W_P  = T_W_Mi × inverse(T_V_Mi) × T_V_P
```

専用検出器が返す`T_C_Mi`は、既知のマーカー実寸とカメラ内部パラメータから求める。同じフレームの`T_W_C`と組み合わせる前に、軸・表裏・回転方向・単位をadapterで正規化する。OpenCV／AprilTagのカメラ座標をThree.jsへそのまま渡さない。

8th Wallの生の座標をW_sdkとし、その尺度がメートルと一致しない場合、上の剛体変換式へ混在させない。マーカー観測から得るメートル単位のカメラ姿勢`T_V_C = T_V_Mi × inverse(T_C_Mi)`と、複数フレームのSDKカメラ姿勢を対応付け、必要な一様尺度・回転・並進を持つ`S_V_Wsdk`を推定する。

```text
S_Wsdk_P = inverse(S_V_Wsdk) × T_V_P
```

ここでSは一様尺度を含む相似変換であり、剛体変換Tと区別する。Three.jsの描画用4×4行列には逆尺度も含め、Presentation内のメートル寸法をSDKのscene unitへ変換する。

尺度推定に十分な並進・観測配置がない場合は較正を確定しない。absolute設定でも実寸との整合を検証し、NORMALという状態だけで尺度の成立を認定しない。SDK再初期化・座標基準の変化が疑われる場合は対応を再検証する。現在は複数姿勢の対応から一様尺度・回転・並進を推定する。観測中に端末の向きをなるべく保った15〜20cmの横方向の平行移動を案内し、静止では確定しない。閾値は実機測定前のPoC設定であり、精度保証ではない。

### 5.3. 複数マーカーと共有原点

配置情報には、会場配置ID・バージョン、ボードID、各マーカーの方式・ファミリー／辞書・ID、実寸とその測定境界、`T_V_Mi`、Presentationの`T_V_P`を持たせる。方式や辞書をまたぐIDの衝突を許さない。既存の原点・publication契約との関係、所有先・取得API・失効条件を確認してから共有schemaを追加する。

ボード内の既知の相対配置と複数の角・観測を使って姿勢を求め、外れ値・配置の不整合・曖昧な姿勢を除外する。単純に複数マーカーの位置を平均するだけで統合済みとしない。検出数・再投影誤差・距離・角度と、実物に対する精度を区別する。

Quest側のArUcoとWeb側の選定マーカーを同じ会場座標へ対応付ける。WebでもArUcoを採用する場合は既存ボードを流用できるか検証し、AprilTagを採用する場合は同一ボード内で相対配置を測って固定する。会場位置が未知の手持ちマーカーは共有原点として扱わない。

### 5.4. 位置保持・再観測補正

現在のPoCはcollecting／locked／invalidと採用理由（移動不足・回転不整合・位置不整合の区別）、推定移動幅と採用標本数の進捗を持ち、複数マーカーの整合確認と再観測補正を実装している。既知配置の全マーカー角をまとめたjoint board PnPで一つの会場対カメラ姿勢を求め、マーカー別の再投影誤差で整合を検査する。直前の有効姿勢をSDK相対運動で伝播した探索候補も追加し、同じ画像誤差で比較する。単なる前値への平滑化で解を固定しない。実機での効果は未確認。

- 初回は複数観測の安定性、尺度、配置との整合を検証して採用する。
- マーカーが見えない間はSLAMで表示を保持する。ただし、この間の真の位置誤差をマーカー残差から観測することはできない。長時間未観測時の再確認条件を測定で定める。
- 再観測時は固定原点との位置・回転・尺度差と観測品質を確認する。整合した観測が継続した場合に、端末ごとの会場対応変換を補正する。微小差の平滑化方法・補正速度は実測で決める。
- 単発の悪観測は補正へ採用せず、確定原点を保持する。否定観測が500ms続く場合は原点を残して表示を停止し、良観測3回で自動復帰する。20cm／0.35rad超の大差は、500ms以内の3観測で候補変換が互いに3cm／0.08rad以内に整合した場合に失効させる。SDK追跡喪失・明示リセットは別の失効原因として扱う。単一フレームへの即時追従や大きな原点ジャンプで隠さない。
- 原点リセット・SDK再起動・会場配置変更時は較正を失効させる。補正は観客のローカル変換に限定し、他端末の共有原点を変更しない。

既存の公開物・配信契約、素材、整合性検証、タイムライン補間を利用する。`unframe-renderer-web`はビルド時に画像を生成する仕組みであり、視聴用Three.js rendererとして組み込まない。既存WebのUnity PreviewをThree.js実装済みと扱わない。

初期表示は焼き込みPNG surfaceに限定し、寸法・透過・レイヤーを再現する。Web用capability profileを追加し、未対応表現は配信選択時に明示的に拒否する。GLB・動画・Native UI相当の対応は、各契約・端末制約を確認した別の追加作業とする。

Realtimeは現在gRPC bidi契約である。ブラウザ向けWebSocket transport adapterを第一候補とし、既存の認証・assignment fencing・viewer投影とsession logicを利用する。通常のgRPC-Webだけでbidi接続できるとは仮定しない。Control/Stateの対応、順序、ACK、backpressure、再接続、snapshot/replayの適用を契約として定める。

視聴専用でもhandshake・ready・ACK等の上り通信は必要となる。UIの非表示だけで操作を制限せず、サーバーがviewer権限を検証する。再生は到着したイベント数ではなくauthoritativeな状態・時刻へ合わせ、途中参加と復帰でも現在の進行に追いつく。

参加方針はログイン不要・ルームID入力で確定する。オーディエンスにアカウント登録や既存ログインを要求しない。ルームは既存Sessionに対応し、別のRoomリソースは作らない。

現行join APIは認証identityを要求するため、そのまま利用できるとは扱わない。Control Planeに匿名オーディエンス向けの参加経路を追加し、入力されたルームIDと参加可能なセッション状態を検証して、サーバー側で匿名participantとviewer専用の参加資格を払い出す。クライアントから任意のroleやparticipant IDを指定して権限を取得できないようにする。匿名参加でもRealtimeと素材配信は発行された参加資格で認可し、閲覧範囲を参加ルームへ限定する。

ルームIDを既存join codeに対応付けるか、Session IDと別の公開用識別子にするかは契約設計時に決める。入力UIの名称はルームIDとし、内部Session IDの直接公開や既存join codeとの同一視は先に確定しない。参加資格の有効期限・再接続・再読み込み時の継続方法、参加試行のレート制限を定義し、ログイン画面への誘導で代替しない。

素材URLの期限更新・CORS・キャッシュ・メモリ上限も定義する。

## 7. 開発順序と受け入れ条件

| 順序 | 作業                                   | 次へ進む条件                                                                                             |
| ---- | -------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| 1    | 設計、基準実装と利用条件の確認         | 未決事項と依存関係、検証方法を記録できた                                                                 |
| 2a   | AprilTag 3／ArUco専用検出器の比較      | 同じ入力・実寸・条件で検出距離、時間、誤検出、姿勢誤差、FPSを測り、実装とファミリー／辞書を選定できた    |
| 2b   | 尺度・カメラ／SLAM座標の対応           | フレーム・軸・内部パラメータを照合し、実測距離とメートル尺度の整合、退化条件での拒否を確認できた         |
| 2c   | 複数マーカーと再観測補正               | 既知配置の統合、遮蔽、画像外の保持、再観測補正、大きな不整合時の停止・復帰を実機で確認できた             |
| 3    | Questとの会場原点比較                  | 同じ実物位置への表示を測定し、座席範囲と許容誤差を確定できた                                             |
| 4    | 既存PNG公開物の再生                    | サイズ・向き・色・透過・レイヤーと非対応表現の拒否が確認できた                                           |
| 5    | ログイン不要のルームID参加とライブ同期 | アカウントなしの参加、viewer権限、無効ID・参加不可状態の拒否、途中参加、進行、切断復帰、失効を検証できた |
| 6    | 複数台・実会場検証                     | 合意した精度・性能・復帰条件を満たし、制約を文書化できた                                                 |

各作業は探索→Red→Green→Refactorで進める。座標変換、状態遷移、順序・重複処理、失効、権限制約に振る舞いのテストを追加する。カメラ追跡や見え方は実機評価を必要とし、モックの成功だけで合格としない。

SDK導入時にバージョンと端末一覧を記録し、ターゲット寸法・距離・角度・照度を揃えて測定する。同じ入力フレームのオフライン比較と、端末の実時間処理を分け、処理解像度・間引き・ファミリー／辞書・パラメータを記録する。初回検出と、近距離で検出した後の保持を混同しない。検証では座席ごとの認識成功率・誤検出率、較正所要時間、位置・角度誤差、数分後のドリフト、FPS、発熱、進行遅延、復帰時間を残す。数値の合格基準は会場の寸法・視聴距離を決めた後、測定前に合意する。

対象領域のcheckを先に実行し、コード変更完了時は `nix run .#check` を実行する。Nix変更時は `nix flake check`、Unity挙動変更時はEditorテストも実行する。新Audienceのcheck/test/build入口をscriptsとflakeへ接続する。コマンドの未実行・失敗と代替検証を記録し、品質コマンドの前後で差分を確認する。
